# news.hako.tokyo 憲法

## コア原則

### I. コード品質と型安全性

すべてのコードはマージ前に `npm run lint` (ESLint) と `npx tsc --noEmit` (strict な
TypeScript) をエラーゼロで通過しなければならない (MUST)。2つのユニット — Collector
スクリプト (`next/scripts/collector/`) と Web フロントエンド (`next/app/`) — は、型を
ローカルで再宣言するのではなく `next/lib/` を通じて共有しなければならない (MUST)。外部
かつ信頼できないデータ (RSS フィード、スクレイピングした HTML、Markdown フロントマター)
は、アプリケーションロジックに入る前に境界で Zod スキーマによって検証しなければならない
(MUST)。境界データに対する `any` や未検証のキャストは禁止する。関数は単一の明確な責務を
持たなければならず (MUST)、デッドコードやコメントアウトされたコードをコミットしてはなら
ない (MUST NOT)。

**根拠**: 本サイトは長期間ほぼ無人で稼働する自動化サイトである。コンパイル時の保証と
検証済みの境界は、誰も実行を監視していない日次ジョブにおける静かな破綻に対する最も安価な
防御策である。

### II. テスト基準 (交渉不可)

データ層ロジック、パース、収集、フィルタリングへのすべての変更は、テストを伴って提供され
なければならない (MUST)。純粋な変換・パースロジックは Vitest の単体テストでカバーしなけれ
ばならず (MUST)、生成入力に対する不変条件 (重複排除、日付フィルタ、slug 生成) は
`fast-check` によるプロパティベーステストを用いるべきである (SHOULD)。ユーザーに見える
ページ挙動は Playwright の e2e テストでカバーしなければならない (MUST)。バグ修正は、修正
前に失敗し修正後に成功する回帰テストを追加しなければならない (MUST)。`main` へのマージ前
に CI で `npm run test:run` が成功しなければならず (MUST)、テストが赤い状態でのマージは
禁止する。

**根拠**: Collector は無人でリポジトリを変更し、フロントエンドはその出力から再ビルドされ
る。テストこそが、パースのエッジケースと本番デプロイの破綻との間に立つ唯一の存在である。

### III. ユーザー体験の一貫性

本サイトは単一の一貫したリストビューを提供する。すべての記事ソース (Zenn、はてな、
Google ニュース、Togetter) は、一貫したレイアウト・タイポグラフィ・日付フォーマットを
持つ単一の共有表示パスを通じてレンダリングしなければならない (MUST)。ソース固有の UI
分岐は禁止する。日付はサイト全体で単一の一貫したタイムゾーン/フォーマットで表示しなけれ
ばならない (MUST)。ページはモバイルとデスクトップで利用可能かつ読みやすく保たれなければ
ならず (MUST)、あるソースが0件を返した場合でも適切に劣化しなければならない (空状態での
クラッシュやレイアウトシフトを起こさない)。ユーザー向けテキストは、サイトの読者層に
合わせて日本語でなければならない (MUST)。

**根拠**: ニュースアグリゲーターの価値は、統一された一覧しやすいフィードにある。ソース
ごとの視覚的な乖離は、いかなる機能の欠落よりも速く信頼性と一覧性を損なう。

### IV. パフォーマンス要件

本サイトは静的生成 (Next.js App Router SSG) でなければならない (MUST)。記事一覧に対する
リクエストごとのサーバーレンダリングやクライアントサイドのデータ取得は行わない。ビルドは
表示ウィンドウ内 (例: 直近3日間) の Markdown ファイルのみを読み込まなければならず (MUST)、
`content/` アーカイブ全体をメモリに読み込んではならない (MUST NOT) — ファイル読込は保存量
ではなく表示量にスケールする。収集リストは境界づけられていなければならず (MUST)
(ソースごとの件数上限と直近フィルタ)、アーカイブが増えてもビルド時間とページ重量を一定に
保つ。ビルド時間やページペイロードがアーカイブ総量に比例して増大する変更は、plan の
Complexity Tracking セクションで正当化しなければならない (MUST)。

**根拠**: `content/` は毎日数十ファイルずつ永遠に増え続ける。アーカイブ総量ではなく表示
ウィンドウにスケールするパフォーマンスこそが、何年先もビルドを高速かつページを軽量に保つ。

## 追加制約 (スタックとアーキテクチャ)

- **ランタイム**: Node.js は `.nvmrc` で固定 (v24.x)。ローカル作業前に `nvm use` を実行する。
- **スタック**: Next.js 16 (App Router, SSG)、React 19、TypeScript (strict)、Tailwind CSS v4、
  検証用の Zod、収集用の `rss-parser` / `cheerio`。
- **2ユニット構成**: Unit 1 = Collector (`next/scripts/collector/`、`npm run collect` で実行、
  `content/{YYYY-MM-DD}-{slug}.md` を書き出す)。Unit 2 = Web フロントエンド (`next/app/`)。
  両者は `content/` にコミットされた Markdown と `next/lib/` の共有型のみを通じて連携する。
- **ストレージ**: Git 上の Markdown ファイルが信頼できる唯一の情報源 (Single Source of Truth)。
  データベースは存在しない。
- **自動運用**: 日次の GitHub Actions ジョブが Collector を実行し `main` へコミットする。
  この push が Vercel デプロイをトリガする。変更はこの無人パイプラインを壊してはならない (MUST NOT)。

## 開発ワークフローと品質ゲート

- すべての作業はフィーチャーブランチを経由する。`main` へのマージは本番デプロイをトリガする
  ため、`main` は常にデプロイ可能でなければならない (MUST)。
- **マージ前ゲート (すべて通過必須)**: `npm run lint`、`npx tsc --noEmit`、`npm run test:run`、
  および `npm run build` の成功。
- 各 PR はコア原則4項目への準拠を確認しなければならない (MUST)。違反は修正するか、plan の
  Complexity Tracking に根拠とともに記録しなければならない。
- 非自明な作業の設計と根拠は `aidlc-docs/` 配下に文書化する。
- ランタイムの開発ガイダンスには `CLAUDE.md` と `aidlc-docs/` を用いる。

## ガバナンス

明示し、下記方針に従ってバージョンをバンプする PR を通じて行わなければならない (MUST)。

**バージョニング方針** (セマンティック):

- **MINOR**: 新しい原則・セクションの追加、または実質的に拡張されたガイダンス。
- **PATCH**: 明確化、文言修正、非意味的な微調整。

**コンプライアンスレビュー**: すべての PR とレビューは、変更がコア原則4項目すべてを尊重し
品質ゲートを通過することを確認しなければならない (MUST)。原則に違反する複雑性は文書で
正当化するか、却下しなければならない。レビュアーは原則 II (テスト基準) を交渉不可として
扱わなければならない (MUST)。
